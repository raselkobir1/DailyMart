DailyMart — System Design

High-level and low-level design for the multi-tenant SaaS departmental-store management system: Tenant/Role/Menu/User/Permission (RBAC), Purchase, Inventory, POS Sales, Dues, Expenses, P&L, Reports, Audit Log and Dashboard. Reflects the architecture defined in CLAUDE.md.

.NET 8 Web API EF Core + PostgreSQL Angular (standalone + signals) Clean Architecture Multi-tenant (shared schema) JWT + RBAC

HLD·1 System Context

Three actors touch the system: a tenant's own staff (Admin, Cashier, ...), the SaaS vendor's platform-admin ops staff, and self-service signups. Everything goes through one Angular SPA and one Web API; in production nginx proxies /api/* so the browser sees a single origin.

HLD·2 Clean Architecture Layers

Dependency direction is one-way: API → Application → Domain and Infrastructure → Application → Domain. Domain has zero outward dependencies. Every layer is internally organized by module folders (Products, Purchases, Sales, ...).

Controllers stay thin — all business rules (stock deduction, due calculation, profit calculation) live in Application-layer services, orchestrated through one IUnitOfWork.

HLD·3 Multi-Tenancy Model

One database, one schema — not database-per-tenant. Every TenantOwnedEntity carries a tenant_id column; isolation is enforced once at the EF Core model level, not per-service, so every existing/future repository query is automatically tenant-scoped.

HLD·5 Key Business Flows

Purchase → Inventory → Supplier Due

  1. Purchase entry increases Product.StockQty per line item.
  2. Every stock-affecting change writes an InventoryTransaction row (traceability, not just a counter).
  3. Credit purchase creates/increases Supplier due; cash purchase does not.
  4. Supplier due always reconciles to unpaid purchases (recompute-and-compare, never trust incremental updates alone).

POS Sale → Inventory → Customer Due

  1. Barcode scan resolves Product; stock can never go negative.
  2. Sale decreases stock; writes an InventoryTransaction (SaleOut).
  3. Cash sale → increases cash balance. Credit sale → increases customer due. Partial payment updates both simultaneously.
  4. Customer due can never go negative; collection is capped at outstanding due.
  5. Profit computed from Sale price vs. Purchase price at line-item level.

RBAC — Login → Permissions → Menu Rendering

  1. JWT carries only the coarse role name ([Authorize(Roles="Admin")] checks).
  2. Fine-grained menu permissions are fetched separately via GET /api/auth/me/permissions — changes take effect without re-issuing tokens.
  3. IFeatureEntitlementService filters out any menu the tenant isn't entitled to before permissions are ever returned.
  4. Angular's canView(menuKey) guard + sidebar both read this permission list.

Self-Service Tenant Signup

  1. POST /api/auth/register → ITenantProvisioningService creates a new Tenant.
  2. Tenant's own "Admin" role is created (per-tenant, not shared globally).
  3. EnsureAdminRoleHasFullMenuAccessAsync grants full CRUD on every generally-available Menu.
  4. Tenant starts on the seeded Free Plan via a new TenantSubscription.

LLD·1 Entity Conventions

Two base types everything inherits from, plus the rules that keep every module consistent.

Base typeFieldsRule
AuditableEntityId (uuid), CreatedAt, CreatedBy, UpdatedAt, UpdatedBy, IsDeleted (bool)Soft delete everywhere — global EF query filter excludes IsDeleted = true.
TenantOwnedEntity : AuditableEntity+ TenantId (uuid, FK → Tenant)Query filter also requires TenantId == CurrentTenantId; FK auto-added via ApplyTenantForeignKeys.

Other invariants: money/quantity columns are always numeric (never float/double); every stock-affecting write also produces an InventoryTransaction row; payment history tables (CustomerPayment, SupplierPayment, SubscriptionPayment) are append-only, never overwritten; naming is snake_case in Postgres, PascalCase in C#.

LLD·4 Service / Repository Design

One IUnitOfWork wraps SaveChangesAsync and repository access. A generic IRepository<T> covers common CRUD; module-specific repositories add custom queries. All business rules live in Application-layer services — controllers only call into services.

LLD·5 Sequence — Login & RBAC Permission Fetch

sequenceDiagram
    actor U as User (browser)
    participant Auth as AuthController
    participant Svc as AuthService
    participant Feat as IFeatureEntitlementService
    participant DB as PostgreSQL

    Svc->>Svc: verify password hash

    U->>Auth: GET /api/auth/me/permissions (Bearer JWT)
    Auth->>Svc: GetMyPermissionsAsync()
    Svc->>Feat: GetEntitledMenuKeysAsync(tenantId)
    Feat-->>Svc: [menuKey, ...] (excludes non-entitled restricted menus)
    Svc->>DB: RoleMenuPermission rows for user's Role ∩ entitled menus
    Svc-->>U: [{menuKey, canView, canCreate, canEdit, canDelete}]

LLD·7 Sequence — Purchase Entry

sequenceDiagram
    actor U as Tenant User
    participant C as PurchasesController
    participant S as PurchaseService
    participant Inv as InventoryService
    participant Sup as SupplierService
    participant UoW as IUnitOfWork
    participant DB as PostgreSQL

    U->>C: POST /api/purchases {supplierId, items[], paidAmount}
    C->>S: CreatePurchaseAsync(dto)
    S->>S: validate items, compute TotalAmount / DueAmount
    S->>UoW: add Purchase + PurchaseItem rows
    S->>Inv: increase Product.StockQty per line, write InventoryTransaction(PurchaseIn)
    S->>Sup: AdjustDueAsync(supplierId, +DueAmount) if credit
    S->>UoW: SaveChangesAsync()
    UoW->>DB: commit (audit interceptor stamps TenantId/CreatedBy, writes AuditLog)
    DB-->>C: success
    C-->>U: 201 Created {purchaseId}

LLD·8 Sequence — POS Sale (Barcode Workflow)

sequenceDiagram
    actor U as Cashier
    participant C as SalesController
    participant S as SaleService
    participant Inv as InventoryService
    participant Cust as CustomerService
    participant UoW as IUnitOfWork
    participant DB as PostgreSQL

    U->>C: scan barcode -> GET /api/products/by-barcode/{code}
    C-->>U: product + price
    U->>C: POST /api/sales {customerId?, items[], paidAmount, paymentType}
    C->>S: CreateSaleAsync(dto)
    S->>Inv: check StockQty >= requested Qty (never negative)
    alt insufficient stock
        S-->>C: 400 Bad Request
    else stock ok
        S->>S: compute SubTotal/Tax(from ShopSettings)/Discount/Total
        S->>UoW: add Sale + SaleItem rows
        S->>Inv: decrease StockQty, write InventoryTransaction(SaleOut)
        alt PaymentType = Credit or Partial
            S->>Cust: AdjustDueAsync(customerId, +DueAmount)
        end
        S->>UoW: SaveChangesAsync()
        UoW->>DB: commit
        DB-->>C: success
        C-->>U: 201 Created {invoice}
        U->>U: print/receipt invoice
    end
